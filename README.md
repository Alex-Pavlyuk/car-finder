# Car Finder

Агент-мониторинг объявлений о продаже авто на **otomoto.pl** и **olx.pl** — двух
площадках, на которые приходится подавляющее большинство объявлений в Польше.
Регулярно обходит выдачу, отсеивает мусор, ранжирует и собирает локальный
HTML-дашборд с подсветкой новинок.

Критерии задаются в `config.yaml`: тип кузова, коробка, привод, год, пробег,
цена, город и радиус поиска. Жёсткие критерии применяются на стороне площадок,
мягкие предпочтения (топливо, конкретные модели) поднимают объявление в выдаче,
а не отсекают.

## Об использовании

Инструмент для личного пользования. Он читает те же публичные страницы, что
видит любой посетитель без входа в аккаунт, с паузами между запросами и
примерно сотней запросов за прогон раз в полчаса. Проверки, которыми площадки
защищаются от автоматики, программа не проходит и не пытается. Всё собранное
— объявления, имена продавцов, тексты — хранится только локально в `data/`
и в репозиторий не входит. Пользуйтесь с уважением к правилам площадок.

## Быстрый старт

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp config.example.yaml config.yaml   # и впишите свой город, бюджет и критерии
```

Собрать приложение и запустить:

```bash
./scripts/build_app.sh && open CarFinder.app
```

`CarFinder.app` живёт **в строке меню** — значок 🚗 в правой части, рядом с
часами, Wi-Fi и Пунктом управления. Окна у приложения нет и иконки в Dock тоже:
это фоновый агент, вся работа с ним идёт через меню значка. Пока приложение
запущено, оно само обходит площадки каждые 30 минут; отдельный планировщик
не нужен.

Если значка не видно, загляните в `data/app.log` — через три секунды после
старта приложение само пишет туда строку вида:

```
значок: заголовок '🚗', x=1019 y=923 w=39, экран 1470 px — на месте
```

`x` — позиция значка в строке меню; ненулевая означает, что он действительно
на экране. Если там `НЕ РАЗМЕЩЁН` (`x=0`), значок не поместился: на MacBook
с вырезом строка меню короче, чем кажется, и лишние значки не рисуются.
Помогает убрать оттуда что-нибудь ненужное (⌘ + перетаскивание значка за
пределы строки). В этом случае приложение ещё и присылает уведомление, чтобы
не приходилось догадываться.

Проверяется именно положение, а не `isVisible`: последний отражает наше же
пожелание показать значок и остаётся `true`, даже когда на экране ничего нет.
Список окон оконного сервера тоже не помощник — без разрешения на запись
экрана он пуст даже для собственных окон процесса.

Меню значка:

| Пункт | Что делает |
|---|---|
| Строка сверху | Итог последнего прогона: сколько подходит, сколько новых, во сколько |
| **Открыть отчёт** | Открывает дашборд в браузере и гасит счётчик новых |
| **Обновить сейчас** | Внеочередной прогон; на время работы значок меняется на 🔄 |
| **Обновлять автоматически** | Выключает и включает таймер |
| **Изменить критерии…** | Открывает `config.yaml` в текстовом редакторе |
| **Показать файлы…** | Открывает папку `data/` с отчётом, базой и логом |
| **Отключить фоновый launchd-агент** | Появляется только если агент установлен — см. ниже |
| **Выход** | Закрывает приложение целиком: прогоны прекращаются, процесса не остаётся |

Значок — единственный индикатор состояния, окна у приложения нет:

| Значок | Состояние |
|---|---|
| 🚗 | работает, ждёт следующего прогона |
| 🚗 3 | то же, и с последнего открытия отчёта появилось 3 новых объявления |
| 🔄 | прогон идёт |
| 🚗 ⏸ | автообновление выключено вручную; «Обновить сейчас» по-прежнему работает |
| ⚠️ | последний прогон упал; причина — в строке состояния и в `data/app.log` |

### Выход, и что после него остаётся

Ничего. Пока значок на месте — приложение работает; исчез значок — процесса
больше нет. «Выход» гасит таймер, прерывает начатый прогон на ближайшем
запросе (а не через минуту) и завершает процесс; если тот почему-то не умер
за 3 секунды, приложение выходит принудительно, чтобы не остаться невидимо
работающим. `kill`, выход из системы и перезагрузка делают то же самое —
приложение слушает SIGTERM.

Прерванный прогон ничего не портит: в базу пишется транзакцией, отчёт
перерисовывается только целиком, а недокачанное просто догрузится в следующий
раз. Проверить, что ничего не осталось:

```bash
pgrep -lf carfinder
```

**Второй экземпляр не запускается.** Замок `data/app.lock` не пускает вторую
копию — вместо неё просто откроется отчёт. Иначе легко получить процесс,
который опрашивает площадки, но значка в строке меню не показывает (в неё
влезает не всё) и потому не закрывается ничем, кроме Мониторинга системы.
Замок держится на `flock`: его снимает ядро, поэтому после `kill -9` или
падения он не «застревает».

**Автозапуск при входе в систему:** Системные настройки → «Основные» →
«Элементы входа» → **+** → выбрать `CarFinder.app`. Приложение удобно сначала
перенести в `/Applications`.

### Одноразовый запуск из терминала

```bash
./run.sh --open
```

Отчёт лежит в `data/report.html` — обычная HTML-страница, открывается двойным
кликом, работает офлайн, тему берёт из системной (тёмная/светлая).

## Как пользоваться отчётом

Подходящих объявлений — сотни, и разгребать их приходится не за один заход.
Поэтому карточку можно отметить **★** или **✕** скрыть; пометки хранятся в
браузере и переживают перегенерацию отчёта, так что скрытое не всплывает
заново после каждого прогона. Вкладки сверху показывают счётчики: подходящие,
почти подходящие, избранное, скрытые. Выбранные фильтры и сортировка тоже
запоминаются.

Ключевое поле на карточке — **«▼ 12 300 zł дешевле похожих»**: отклонение от
ожидаемой цены по этой же модели с поправкой на пробег. Сортировка «Выгоднее
к похожим» ставит такие объявления наверх. Там же — сколько дней объявление
висит (после 45 дней подсвечивается: либо переоценено, либо с ним что-то не
так) и мини-график, если цена менялась.

Два ползунка сужают выдачу: **расстояние** (например, 40 км вместо полного часа
езды) и **«на сайте»** — скрывает залежавшиеся объявления. Второй по умолчанию
стоит на 100 днях: долго висящее объявление обычно переоценено, свежие
разбирают быстро. Это именно фильтр отображения, а не отбраковка — объявления
собираются все, и ползунок в любой момент сдвигается на «любой срок».
Начальное положение задаётся в `config.yaml` (`report.max_days_default`).

Заголовки, города и ссылки в отчёте — текст, который пишет продавец, то есть
данные из интернета. В разметку он попадает только через `esc()`, а в `href`
и `src` пускаются только `http(s)`-адреса: иначе заголовок вида
`<img src=x onerror=…>` выполнял бы свой код на странице отчёта — стирал
пометки ★ в localStorage или отправлял содержимое отчёта наружу. Тест
`test_untrusted_fields_are_escaped_in_template` следит, чтобы при правках
шаблона ни одно такое поле не осталось без обёртки.

## Команды

| Команда | Что делает |
|---|---|
| `./run.sh` | один прогон, обновляет `data/report.html` |
| `./run.sh --open` | то же + открыть отчёт в браузере |
| `.venv/bin/python -m carfinder watch --interval 30` | крутится в терминале, обновляет каждые 30 мин; тот же замок, что у приложения — вместе они не запустятся |
| `.venv/bin/python -m carfinder urls` | печатает поисковые ссылки — можно открыть в браузере и сверить фильтры руками |
| `.venv/bin/python -m pytest tests -q` | тесты |

## Фоновый режим через launchd

Альтернатива приложению — для случая, когда значок в строке меню не нужен,
а прогоны должны идти всегда, даже если приложение не запущено.

**Это единственное, что продолжает работать после выхода из приложения** —
на то он и системный агент. Поэтому включайте что-то одно: с launchd-агентом
и `CarFinder.app` разом площадки опрашиваются вдвое чаще без всякой пользы.
Если агент установлен, приложение при старте это заметит, скажет об этом
уведомлением и добавит в меню пункт **«Отключить фоновый launchd-агент»** —
он выгружает агента и удаляет plist.

```bash
cp scripts/com.carfinder.watch.plist ~/Library/LaunchAgents/ && launchctl load ~/Library/LaunchAgents/com.carfinder.watch.plist
```

Прогон будет запускаться каждые 30 минут, лог — в `data/watch.log`.
Отключить:

```bash
launchctl unload ~/Library/LaunchAgents/com.carfinder.watch.plist
```

## Что происходит внутри

```
otomoto ─┐                                     ┌─ проверка описаний ─┐
         ├─ склейка дублей ─ фильтры ─ оценка ─┤                     ├─ SQLite ─ HTML ─ уведомление
olx ─────┘                            цены     └─ текст на фото ─────┘
```

1. **Сбор.** Все жёсткие критерии передаются самим площадкам в поисковом
   запросе, поэтому качаются только релевантные страницы. Цена и год
   запрашиваются с небольшим запасом — из этого запаса формируется вкладка
   «Почти подходят».
2. **Склейка дублей.** OLX зеркалит бóльшую часть объявлений салонов с otomoto
   (~40% выдачи). Основной записью берётся otomoto — там аккуратные поля;
   из OLX-копии подтягиваются координаты и полное описание.
3. **Фильтры.** Цена, год, пробег, кузов, коробка, привод. Незаполненные поля
   достраиваются по тексту: `xDrive20d`, `4Matic`, `AllGrip` → полный привод,
   `instalacja gazowa` → ГБО.
4. **Оценка цены.** Ожидаемая цена по сопоставимым объявлениям — только той же
   марки и модели, с поправкой на пробег. Сравнение по марке пробовали, и оно
   врёт: Audi Q7 попадала в одну группу с A3. Оценку получают ~80% выдачи;
   это честнее, чем 100% мусорных оценок. Резко заниженная цена почти всегда
   означает скрытую проблему — такие объявления не выбрасываются, но
   помечаются и опускаются в рейтинге.
5. **Проверка описаний и фотографий.** Отсеивает то, чего не видно по полям
   объявления (подробнее ниже).
6. **Скоринг** 0–100, все веса — в `config.yaml`. На карточке раскрывается
   разбивка по слагаемым: видно, почему объявление оказалось наверху.
7. **SQLite** (`data/listings.db`) помнит, что уже видели: отсюда бейджи
   «НОВОЕ» и «−5 000 zł», история цен, а также кеши проверок и справочник
   координат городов.
8. **Уведомление macOS** — только про новые объявления с рейтингом выше
   `notify.min_score` и не больше пяти за раз, иначе оно превращается в шум.
   На первом прогоне не отправляется: там новыми были бы все 500.

## Что отсеивается и почему

Фильтры площадок работают по полям, которые заполняет продавец, и не ловят
целые классы мусора. Всё перечисленное встретилось на реальной выдаче:

| Что | Как выглядело |
|---|---|
| Битые машины | Toyota RAV4 2021 Hybrid за 29 900 zł, в описании «Samochód uszkodzony jak na zdjęciach». Признак повреждения otomoto в выдаче **не отдаёт вообще** — отсекается фильтром на стороне сайта плюс проверкой текста |
| Авто под заказ из США | Jeep Grand Cherokee 2021 за 29 999 zł, «Auto do sprowadzenia z USA. Jest to cena szacowana» — машины в Польше нет, цена вымышленная |
| Цессия лизинга | В цене указан взнос, а не стоимость автомобиля |
| Бронь и «продано» | «SAMOCHÓD JUŻ ZAREZERWOWANY PRZEZ INNEGO KLIENTA» — в описании или **прямо на фото** |

Всё перечисленное выбрасывается из выдачи. Мягкими остаются только «cena netto»
и указание задатка — они показываются жёлтым предупреждением на карточке:
у салонов это часто шаблонный текст, оставляющий в поле цены сумму брутто,
и отбраковка по ним давала слишком много ложных срабатываний.

Описания OLX приходят вместе с выдачей — бесплатно. У otomoto нужен отдельный
запрос страницы объявления, поэтому вердикт **кешируется навсегда**: каждое
объявление проверяется ровно один раз за свою жизнь. За прогон — не больше
`verify.max_per_run` загрузок, начиная с самых перспективных.

### Отметки на фотографии

Часть салонов о брони не пишет вовсе, а закрывает первое фото баннером
«REZERWACJA». В данных такое объявление ничем не отличается от свободного:
цена, пробег и текст обычные, а картинка у каждого своя — по совпадению URL
их тоже не поймать. Информация есть только в пикселях.

Поэтому превью прогоняется через распознаватель текста **Vision, встроенный
в macOS**: офлайн, без внешних сервисов и без tesseract. На настоящих фото
он читает разве что номерной знак, а баннеры видит уверенно. Результат
кешируется по URL картинки, так что повторные прогоны бесплатны; полный обход
выдачи занимает около двух минут и делается один раз.

Если `pyobjc-framework-Vision` не установлен или система не macOS, шаг молча
выключается — остальной конвейер работает как раньше.

## Настройка

Всё в `config.yaml` (в репозитории лежит `config.example.yaml` с нейтральными
значениями — скопируйте и впишите своё). Перезапуск не требует изменений кода.

**Расширить поиск на другие кузова** — `criteria.body_types`, допустимо:
`suv`, `combi`, `compact`, `minivan`, `sedan`, `city-car`, `mini`, `coupe`, `cabrio`.

**Разрешить передний привод** — убрать из `criteria.drives` лишнее или очистить
список целиком.

**Сменить город/радиус** — `location.city` (латиницей, как в URL площадки) плюс
`city_lat`/`city_lon` для расчёта расстояния. Радиус — одно из значений,
которые понимают оба сайта: 5, 10, 15, 25, 50, 75, 100, 150.

**Поднять конкретные модели** — `scoring.model_bonus`, подстрока ищется в
«марка модель версия».

После правки проверьте, что запросы собрались как надо:

```bash
.venv/bin/python -m carfinder urls
```

## Устойчивость

Обе площадки обслуживают только клиентов с браузерным TLS-рукопожатием:
обычный `requests` они не принимают (403 ещё до заголовков). Поэтому HTTP-клиент
здесь `curl_cffi` с TLS-стеком браузера — это единственная причина, по которой
он тут нужен. Между запросами выдерживается пауза (`runtime.request_delay_sec`),
на ошибках — повтор с нарастающей задержкой.

`CarFinder.app` — обычный бандл вокруг того же кода, без py2app: он запускает
интерпретатор из `.venv` проекта, поэтому правки в `carfinder/` и `config.yaml`
подхватываются сразу, без пересборки, а сам бандл весит килобайты. Обратная
сторона — приложение привязано к этой папке и не переносится на другой
компьютер; для личного инструмента это разумный размен.

Ещё четыре ловушки, из-за которых приложение выглядит нерабочим, и все решаются
только в коде:

**`LSUIElement` в нашем Info.plist ни на что не влияет.** PyObjC для доступа
к GUI перезапускает процесс через системный `Python.app`, и Dock смотрит уже
в его Info.plist — в Dock появляется иконка-ракета, а значка в строке меню
будто и нет. Лечится программно: `setActivationPolicy_(Accessory)` при старте.
Проверить можно так — должно быть `UIElement`:

```bash
lsappinfo info -only ApplicationType $(pgrep -f carfinder.app | head -1)
```

**Интерфейс нельзя трогать из фонового потока.** Прогон идёт минуту и обязан
быть фоновым, но прямое присваивание `self.title` из потока приводит к тому,
что значок не появляется вовсе. Поэтому поток только считает, а результат
уходит в главный поток через `AppHelper.callAfter`.

**Сигналы не доходят, пока крутится рун-луп.** Обычный `signal.signal`
в Cocoa-приложении бесполезен: Python исполняет обработчик только когда
управление возвращается в интерпретатор, а главный поток сидит внутри
`AppHelper.runEventLoop` и вернётся оттуда на следующем тике таймера — через
полчаса. То есть `kill` и выход из системы приложение попросту не закрывали бы.
Решение в `carfinder/lifecycle.py`: `set_wakeup_fd` пишет номер сигнала в трубу
прямо из C-обработчика, а забирает его отдельный поток. Там же — замок
единственного экземпляра, и по тем же соображениям «процесс, которого не видно,
всё равно работает».

**Запуск через `exec` из бандла лишает приложение значка.** Продолжение той же
истории с `Python.app`: при `exec` процессом, который Launch Services
зарегистрировал как `CarFinder.app`, оказывается бинарник чужого бандла.
Приложение по учётам системы одно, исполняемый файл принадлежит другому — и
в этом состоянии macOS значок создаёт, но места в строке меню ему не выделяет.
Ни ошибки, ни признака: `isVisible` — `true`, координаты нулевые, на экране
пусто. Тот же скрипт из терминала работает, потому что там регистрации
`CarFinder.app` нет вообще. Поэтому launcher бандла запускает Python
отсоединённым (`&` и сразу `exit 0`) — тот регистрируется в системе сам,
как при запуске из терминала.

Запускающий скрипт бандла вызывает Python через `arch -arm64`. Это обязательно:
Python с python.org — universal-бинарь, и при старте через Launch Services macOS
выбирает из него x86_64-срез под Rosetta, тогда как колёса в `.venv` собраны под
arm64. Без этого приложение стартует, но каждый прогон падает на
`incompatible architecture` при импорте `curl_cffi`. Архитектура подставляется
из `uname -m`, так что на Intel-маке соберётся правильно.

Данные берутся из JSON, встроенного в страницу выдачи (`__NEXT_DATA__` у
otomoto, `__PRERENDERED_STATE__` у OLX), а не из разметки — это заметно
устойчивее к редизайну. Если площадка всё же поменяет структуру, в логе будет
`не найден advertSearch` / `не найден __PRERENDERED_STATE__`, а вторая площадка
продолжит работать: падение одного источника не роняет прогон.
